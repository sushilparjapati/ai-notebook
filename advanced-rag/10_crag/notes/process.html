Revision Notes · RAG Series

Corrective RAG

A retriever that checks its own work — graded, corrected, and re-sourced before it's allowed to answer.

Self-Correcting

Why bother correcting retrieval?

Plain RAG retrieves once and trusts it completely. CRAG grades what came back before letting it near the answer.

✕ Naive RAG

retrieves once, never checks

question→ retrieve→ generate

If the 4 retrieved chunks are irrelevant, the model never finds out — it answers from them anyway.

✓ Corrective RAG

retrieves, grades, then decides

question→ retrieve→ evaluate→ ⋯

A grade decides what happens next: trust it, replace it with a web search, or blend both.

The evaluator's three verdicts

Each retrieved chunk gets a relevance score 0–1. Two thresholds (0.7 / 0.3) turn the set of scores into one verdict — like a traffic light for what happens next.

Correct
at least one chunk scores > 0.7
↓
refine internal docs, answer from them
Ambiguous
mixed — nothing great, not all bad
↓
refine internal docs + search the web, combine
Incorrect
every chunk scores < 0.3
↓
discard internal docs, search the web instead

Knowledge refinement — decompose → filter → recompose

A retrieved chunk is rarely 100% relevant. CRAG splits it into sentence "strips," keeps only the ones that answer the question, then glues those back together.

question → “Explain the bias–variance tradeoff”

keep"Bias… is due to wrong assumptions, such as assuming the data is linear when it is actually quadratic."
keep"A high-bias model is most likely to underfit the training data."
drop"Irreducible error — this part is due to the noisiness of the data itself."
drop"Regularized Linear Models — a good way to reduce overfitting is to regularize the model."
keep"There is a trade-off between bias and variance… flexible models have low bias and high variance."
Recomposed → refined_contextOnly the 3 kept sentences are joined and handed to the generator — the tangents about irreducible error and regularization never reach the prompt.

Glossary

strips
Sentences produced by splitting a chunk — the smallest unit CRAG filters at.
refine()
Decompose → filter → recompose: the knowledge-refinement step every path shares.
verdict
CORRECT / INCORRECT / AMBIGUOUS — the 3-way call derived from chunk scores.
UPPER_TH / LOWER_TH
0.7 and 0.3 — the two cutoffs that turn scores into a verdict.
query rewrite
Turning a natural question into a short keyword query for the web search tool.
corrective action
The paper's term for "go get better knowledge" — here, a web search.

Self-test

Why not just always web search and skip the evaluator?
When internal retrieval is already good, web search only adds latency, cost, and less-curated sources. The evaluator lets you keep the cheap internal path whenever it's actually sufficient.
Why filter sentence-by-sentence instead of whole chunks?
A chunk is rarely all-relevant or all-irrelevant. Sentence-level filtering keeps the one useful line inside an otherwise noisy chunk, instead of keeping (or discarding) the whole thing.
What's the real difference between how INCORRECT and AMBIGUOUS are handled?
Both trigger rewrite → web search. The difference is only inside refine(): INCORRECT uses web_docs only; AMBIGUOUS uses good_docs + web_docs together.
What do the two thresholds actually gate?
UPPER_TH (0.7) asks "is any single chunk good enough to trust alone?" → CORRECT. LOWER_TH (0.3) asks "is this chunk worth keeping at all?" — used both for the INCORRECT check (all below it) and for building good_docs (kept if above it).
