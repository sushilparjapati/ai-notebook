Graph RAG

Some answers are a path through several facts, not a single passage — so retrieval becomes a graph traversal, not a similarity search.

Multi-Hop
Requires a free Neo4j AuraDB instance before running — see ../SETUP.md. Run 01_ingestion.ipynb before 02_retrieval.ipynb, or the graph is empty.

Why can't chunk similarity answer this?

Every other technique in this repo retrieves by embedding similarity. That works when one passage contains the whole answer. It fails when the answer is a chain of facts spread across separate passages.

✕ Chunk similarity

"What product did the org whose board Elon Musk left release?"

similarity search →
one chunk about "left the board"
or
one chunk about "released a product"
— never both at once

No single chunk's embedding is close to the full question, because no chunk contains the two-step answer.

✓ Graph traversal

same question

Cypher:
Person -[LEFT_BOARD]-> Org -[RELEASED]-> Product
→ Chatgpt

The retrieval mechanism itself walks the two-hop path — because the index is a graph, not a bag of chunks.

Retrieval — the Cypher-generation gotchas

The question → Cypher prompt is hand-tuned with rules the model got wrong by default. Worth knowing as real graph-RAG lessons, not just theory.

RuleWhy it's needed
[:TYPE1|TYPE2] — colon only on first typeNeo4j 5+ syntax; a colon before every type is an error
toLower(n.id) = toLower("SpaceX")LLMGraphTransformer title-cases ids ("SpaceX" → "Spacex") — exact match silently returns nothing
toLower(p.id) CONTAINS 'elon' AND CONTAINS 'musk'names get stored in partial/abbreviated forms across chunks

Self-test

Why does chunk-similarity retrieval fail on the "board → product" question?
The sentence about leaving the board and the sentence about the product release are in different, unrelated chunks — no chunk's embedding is close to the full question because no chunk contains the two-step answer.
Why title-case and CONTAINS matching instead of exact match?
LLMGraphTransformer normalizes entity ids inconsistently across extraction calls (case, partial names) — the query layer has to compensate, or real matches get silently missed.
Why also build a vector index over Document nodes if retrieval uses Cypher?
Keeps hybrid retrieval possible from the same ingested data — similarity search for open-ended questions, graph traversal for multi-hop ones. This build only exercises the Cypher path.
How does this differ from Microsoft's "GraphRAG" (community summaries)?
That variant clusters the graph and summarizes each cluster for global thematic questions. This build traverses the raw graph directly per-question for multi-hop factual questions — same "build a graph first" instinct, different downstream use.
