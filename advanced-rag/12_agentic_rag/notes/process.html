Agentic RAG

No fixed routing left — the model itself decides which tools to call, how many times, and in what order.

Tool-Calling Loop

Why hand the routing to the model?

CRAG and Self-RAG still run a fixed graph — a verdict or reflection token picks a branch you wrote in advance. Agentic RAG removes the preset branches entirely: the model calls real tools, on its own judgement, for as many rounds as it decides it needs.

✕ Fixed graph

CRAG / Self-RAG style

question→ router node→ retrieve→ generate

The routing logic is code you wrote in advance — an if/else, a threshold, a token.

✓ Agentic RAG

tool-calling loop

question→ agent (LLM)⇄ tools→ generate

The routing logic is the model's own tool-call decision, made fresh every turn.

The agent decides: one tool, both, or neither

Evaluate → rewrite → retry

After tool calls return, a relevance filter checks the docs (the same instinct as CRAG's evaluator / Self-RAG's ISREL) — and a failed check triggers a query rewrite, not a dead end.

"how long people take to get rid of their vehicles completely as per the report?"
informally phrased, but 1 relevant doc found immediately — no rewrite needed
is_relevant: True (rewrite_count: 0)
"What does the report say about nuclear power?"
off-topic for the PDF — triggers rewrite; the agent's web_search tool then pulls in a relevant nuclear-energy result
is_relevant: True after 2 rewrites

Query decomposition — split before you retrieve

A compound question gets split into focused sub-queries before the agent starts calling tools — otherwise one retrieval call skews toward whichever topic dominates the embedding.

"Impact of EVs on the oil industry, and what is the current price of Brent Crude" → decomposed into:

  1. Step 1 historical impact of EV adoption on oil demand
  2. Step 2 major energy outlooks' 2030/2040 projections
  3. Step 3 gasoline/diesel consumption trends by market
  4. Step 4 impacts on oil industry finances/capex
  5. Step 5 effects on refining demand and margins
  6. Step 6 how oil companies adjusted corporate strategy
  7. Step 7 current spot price of Brent crude

Glossary

tool-calling agent
an LLM bound to callable tools, deciding per-turn whether/which to call.
vector_store_search / web_search
the two tools available — internal corpus vs. live web.
retrieval round
one agent → tool → agent cycle; capped by max_retrieval_steps.
evaluate_docs
post-retrieval relevance filter — same idea as CRAG's evaluator.
rewrite_query
rephrases the question and retries when nothing relevant came back.
build_prompt
assembles the generation prompt from what happened this turn.

Self-test

Why tool-calling instead of just more if/else branches?
Tool-calling lets the model decide, per query, how many tools to use and in what combination — the "both tools in one turn" case isn't expressible cleanly as a fixed set of hardcoded branches, especially as more tools get added.
Why does the retry cap from step 03 matter if step 02 already worked fine?
An agent loop has no built-in stopping guarantee — the cap is a safety net for queries or models that keep generating tool calls without converging.
Why decompose before retrieving, not after seeing an incomplete answer?
A single retrieval call on a multi-topic question skews toward whichever topic dominates the query's embedding, starving the other sub-topics of any retrieval at all.
How does evaluate_docs/rewrite_query here relate to CRAG's evaluator and Self-RAG's ISREL loop?
Same underlying idea — grade retrieval, replace it with a better query if bad — but here it's one capability inside an open-ended agent loop, not the entire pipeline's structure.
